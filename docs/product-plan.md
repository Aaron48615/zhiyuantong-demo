# 智愿通产品方案

## 需求与用户

目标用户是已经出分、有初步专业方向的上海普通本科考生。用户需要知道哪些选择符合选科条件、哪些更接近自己的偏好，以及在学校、专业、城市和费用之间如何比较。原型以一条可操作的流程验证这些需求：填写档案与偏好，查看推荐理由，进入详情，比较两到三项，保存并整理候选。

首版的交付重点是前端产品设计与页面实现，并明确未来的数据和后端职责。它不提供正式报考提交、录取保证或经过验证的预测模型。数据不完整时显示来源和不足，避免把模型生成文本或模拟数字包装成真实结论。

## 项目范围

包含学校八维与专业六维评分、就业分析、九项偏好、模拟风险分档、推荐、对比和六类问答。默认展示地域、城市类别、学校综合排名、专业排名、专业师资力量；就业质量、考公考编友好度、创新能力、费用放在表单提交按钮上方的进阶设置中。收起只影响显示，不停用这些权重。

考生基础信息、默认偏好、候选和对比选择保存在本机。首版不做账号、短信、支付、后台管理、全国政策配置或生产数据采集平台。React Native 只安排为后置对照，不重复建设全部 Vue 页面。

页面先采用简单样式。后续视觉调整按照确认后的设计稿执行，功能字段、数据来源提示、错误状态和手机适配仍需保留。

## 上海场景与数据边界

2026 年普通本科以院校专业组为填报单位：最多 24 组，每组 4 个专业并选择愿否调剂，调剂限组内。原型保留学校、专业组、专业三层关系，选科是推荐前的资格过滤。收藏的是学校专业候选，不能直接导出为正式志愿表。

官方成绩分布用于同分位次区间参考，真实规则与历史专业组投档资料列明来源。专业设置、组构成、评分、位次和就业使用固定种子模拟。50 所学校各有 6 条专业样本，共 300 条，保证学校引用、比例总和、历史年份和就业口径一致。所有模拟值都不表示真实高校事实。

站在 2026 年填报期，只参考此前三年录取资料；2026 年最终结果不能作为该次推荐的输入。相同专业组代码也不保证跨年专业构成一致，正式服务需要维护组变更记录。

## 推荐与解释

先过滤选科不符合的项目，再按意向专业筛选。九项偏好评分均归一到 0—100，用用户权重计算加权总分。地域与城市不匹配会降低对应得分；费用超出预算会降低费用匹配分；学校与专业评分使用各自维度平均值。这些是透明的原型规则，实际评分口径仍需数据团队与业务人员论证。

风险分档独立展示。使用考生位次与前三年模拟专业位次中位数之比，按 0.85、1.05 两个阈值分档；数据不足不评估。标签不是统计概率，阈值尚未校准。详情展示每项得分、权重及贡献，供用户理解推荐为何发生变化。

学校八维和专业六维的原型评分由固定种子在指定区间生成，明确标记模拟。未来可分别从科研和学科评估、教学资源、就业调查、设施调查、教师结构、交流项目、学生调查、历年投入构建学校指标；专业指标采用学科评估、课程结构、教师背景、升学、薪资与认证。每个原始指标需要固定统计年份、缺失值规则、异常值处理、归一化方法和来源，不能直接把随机评分替换成来源混杂的“综合排名”。

## 问答设计

支持政策、专业解读、就业、择校、偏好推荐、数据分析。基础版使用关键词和对话上下文检索，回答读取同一数据体系。DeepSeek 接入后在服务端接收查询依据并组织回答，不直接生成数据库中不存在的事实。无数据、模型超时和限流要有明确提示。当前规则理解能力有限，不承诺处理所有自然语言表达。

## 技术与实现分工

Vue 3 与 TypeScript 适合现有技能基础；Vue Router 管理页面；Pinia 保存跨页面档案和选择；Axios 把页面与服务接口分开；ECharts 处理雷达、分布和趋势图。核心逻辑使用普通 TypeScript 函数，方便测试和未来迁移到服务端或 RN。前端使用按路由加载，图表库在进入详情时加载。

Node.js 本机服务提供推荐 API 和模型代理示例，不引入数据库。生产阶段由后端提供权威数据与校验、用户与方案持久化、推荐版本管理、模型凭证及限流、日志与审计。前端负责表单、反馈、信息展示和交互，不把浏览器里的模拟数据或计算当作权威服务。

## 九天内的阶段安排

| 阶段       | 建议投入  | 交付与验收                                                   |
| ---------- | --------- | ------------------------------------------------------------ |
| 范围与规则 | 第 1 天   | 场景、范围、数据来源、页面与字段确认                         |
| 主流程     | 第 2—4 天 | 档案、偏好、推荐、详情、收藏、对比可操作                     |
| 问答与接口 | 第 5 天   | 六类基础问答；可选模型接入；接口说明                         |
| 样式与检查 | 第 6 天   | 按确认后的视觉方案调整，检查手机与桌面                       |
| 阅读与讲解 | 第 7—8 天 | 能解释状态流转、数组方法、请求、图表与规则；亲自完成少量修改 |
| 演练与缓冲 | 第 9 天   | 录屏、运行复查、准备设计取舍与后端分工说明                   |

这是时间分配建议，阶段按验收结果推进。若时间不足，优先保留主流程、数据说明和讲解，RN 对照页后置。

## 验证与展示

自动测试关注选科资格、权重总和、排序、数据参照完整性、比例、时间边界和上下文。浏览器检查覆盖表单错误、进阶设置、空结果、收藏持久化、对比数量、详情图表和问答回退。性能目标为推荐在普通移动设备上 3 秒内生成；本地计算测试不代表已完成真实移动设备性能验收。

展示时使用一份预设档案，先解释为什么要区分匹配与风险，再改变地域或就业权重，比较结果，保存候选并向助手追问。讨论中明确说明真实数据接入、评分口径和预测校准仍需后续工作。

## 动态预测模型思考

升级动态预测前，需要按省份、批次和年份整理招生计划、专业组及专业构成、选科要求、分数位次分布和历史录取结果，并记录各字段在填报时是否已经可获得。报考热度可使用合规授权的咨询、收藏和搜索汇总指标，但要评估平台用户与全部考生之间的样本偏差。计划变化与组内专业调整应显式建模，“大小年”只作为待验证现象，不能预设固定周期。实现时先建立位次匹配基线，再尝试逻辑回归、梯度提升树或分位数回归，估计录取位次区间或经校准的概率；稀疏样本和新设专业组应扩大不确定区间，避免强行给出点预测。评估采用按年份滚动的回测，严格禁止把当年最终录取结果或填报结束后的热度作为输入。除排序能力外，应检查概率校准、区间覆盖率，以及不同分数段和学校类型的误差，并评估误判为安全的代价。上线先小范围观察，保留模型版本、数据快照和人工核查入口，持续与简单基线比较。
